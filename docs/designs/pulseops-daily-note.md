# Design: PulseOps, a daily ops note for a one-person fleet

Generated by /office-hours on 2026-11-09
Branch: main
Repo: haivx/pulseops
Status: DRAFT
Mode: Builder

## Problem Statement

I run 2-4 production apps of my own. They are new, with few users, and have had no real incident yet. To feel safe I check several places by hand: each app's hosting dashboard, the Anthropic console for LLM usage, the domain registrar, and billing emails for subscriptions. It is hard to keep track of.

The problem is reassurance across too many tabs. It is not diagnosis.

PulseOps is a personal tool, a portfolio project, and the project I am using to learn gstack. There is no revenue goal.

## What Makes This Cool

Ops tools assume you want a console, but a console is one more tab. PulseOps v1 has no console. It is one message each morning, watched by an outside service, so the checker cannot die silently. The portfolio story is one person running a small production fleet from a single message, on a small data path with a strict privacy boundary.

## Constraints

- One user, 2-4 apps, hosted on Railway, Vercel or elsewhere. Nothing in the design assumes one host, and apps on one host must not depend on that host's API for their row in the note.
- All apps are TypeScript/Node, so there is one client file.
- The Anthropic account is individual. Anthropic's docs say the Admin API, which holds the usage and cost reports, is unavailable to individual accounts. LLM spend must come from usage the apps log themselves.
- Telemetry must never carry prompts, responses, document IDs or user data.
- Telemetry must never break or slow an app.
- The repo is a portfolio piece, so assume it may be public. App names, the subscription list and tokens stay out of git.
- v1 stays small, and it must not block v2.

## Premises

Agreed in session:

1. The problem is reassurance across too many tabs. Diagnosis, logs and incident timelines are out of v1.
2. v1 has no console. It is a daily message, and the detail page comes later.
3. Buy probes and dead man's switches. Build only the note, the collector and a hand-kept subscription list. Email parsing is out.
4. LLM spend comes from usage the apps log themselves, because the account is individual.
5. An outside service watches the job, so an outage at a hosting provider cannot silence both the apps and the checker.

## Approaches Considered

### Approach A: Pull from each app
Each app keeps its own usage table and exposes a private endpoint. Rejected: it repeats the work in every app, and v2 would start with a migration to central storage.

### Approach B: Small collector with one events table (chosen)
Apps send usage through a non-blocking client to one ingest endpoint backed by Postgres. A scheduled job reads the table and sends the note.

### Approach C: Structured logs read through Railway's API
Rejected: it depends on log retention and query limits that were not verified, and it ties the data path to Railway.

## Recommended Approach

Approach B. The event shape already carries most of v2's fields, so v2 needs only small additive migrations instead of moving to central storage.

### Build versus buy

| Need | Decision |
|---|---|
| App down, immediate alert | Buy: Better Stack probes (free tier reported at 10 monitors; 2-4 apps plus the collector fits) |
| Worker silent, immediate alert | Buy: one healthchecks.io check per worker (free tier reported at 20 checks) |
| Collector silent | Buy: its own healthchecks.io check, plus a Better Stack probe on its health endpoint |
| Daily note job died | Buy: its own healthchecks.io check |
| Daily note, LLM usage collection, subscriptions due | Build: this is PulseOps |

Immediate alerts go directly from the bought tools to me. PulseOps is never in that path, so a PulseOps bug cannot suppress an alert.

Worker pings are a small change in each app, separate from the PulseOps client. A long-running worker sends an HTTP GET to its healthchecks.io URL from its main loop every 5 minutes, with a 2-second timeout and errors ignored, and the check has a 15-minute grace period. Pinging from the main loop means a hung worker stops pinging too, and also means a single job longer than 5 + 15 = 20 minutes would raise a false alert, so set the grace above the longest expected job. A scheduled job pings once on success.

### Components

1. **Client:** one small TypeScript file vendored into each app that makes LLM calls. Apps with no LLM calls, such as a static site on Vercel, are probe-only and have no client.
2. **Collector:** one HTTP service with Postgres, on any host that can also run a scheduled job. The apps' hosts play no part in this choice.
3. **Note job:** a scheduled run that reads all sources and sends one message.

### Deploy status

Deploy status is optional and is read when the note runs, so there is no webhook endpoint in v1. Every source is normalized to one shape:

```ts
type DeployEvent = {
  app: string;
  source: string; // "github", or a platform adapter's name
  state: "success" | "failure" | "in_progress" | "none" | "unknown";
  at: string | null; // when that state was reported
};
```

- Each app names its source in the registry: `github` (with a repo and environment), a platform adapter, or `none`.
- GitHub's deployment statuses are the first source, because one adapter can cover any host that reports deployments to GitHub.
- A platform adapter is written only for an app that GitHub cannot cover. Each adapter is one function that takes the app's config and returns a `DeployEvent`.
- An adapter that fails returns `unknown`, which prints as `unknown: <source> unavailable`.

### Event schema (strict allow-list)

Batch envelope, and no other fields:

| Field | Rule |
|---|---|
| `v` | exactly `1` |
| `batch_id` | a UUID |
| `app` | a registered app name that matches the app bound to the bearer token |
| `process` | a process name registered for that app, such as `web` or `worker` |
| `dropped` | integer from 0 to 1,000,000 |
| `events` | array of 0 to 100 events |

Event fields, and no others:

| Field | Rule |
|---|---|
| `step` | one of the steps registered for that app |
| `model` | matches `^[a-z0-9_.:-]{1,64}$` |
| `input_tokens`, `output_tokens` | integers from 0 to 10,000,000 |
| `latency_ms` | integer from 0 to 3,600,000 |
| `status` | `ok` or `error` |
| `error_class` | one of `rate_limited`, `timeout`, `overloaded`, `auth`, `invalid_request`, `server_error`, `other`. Required when `status` is `error`, absent otherwise |

- Any unknown field or invalid value, at either level, rejects the whole batch. A batch over 256 KB is also rejected.
- **What the boundary guarantees:** field names, `step` and `error_class` are closed sets enforced by the server, so a document ID or user value cannot pass through them. `model` is only a shape check, so a value such as `doc-8841` would match. The rule that keeps it clean is that `model` comes from code or config, never from user input. `model` is not a closed set because a new model should show as `unpriced` in the note instead of losing the batch.
- Adding a step means updating the registry before deploying the app. If that is missed, batches are rejected and the headline reports it.
- Error messages are never sent.
- The server records the time a batch was received and uses it to assign events to a day. Events carry no timestamp of their own, which keeps to the agreed field list. Events flushed just after midnight count toward the new day, which is acceptable for an estimate.
- `dropped` is a count of events the client discarded, as defined under client behaviour. It carries no event content.
- **Why v1 collects fields the note does not use:** `step`, `latency_ms`, `status` and `error_class` serve v2, not the v1 note. I am keeping them so v2 starts with real history. The cost is keeping the step list current in the registry. Deferring them through the `v: 2` rollout would shrink v1, but that history would be lost.

### App registry

A git-ignored `fleet.yaml` is the only list of what exists, and the repo commits only `fleet.example.yaml`. For each app it holds:

- The name and its monitor IDs: Better Stack monitor, and healthchecks.io checks if it has workers.
- Its deploy source, as described under Deploy status.
- For an app with a client: one or two token hashes, its allowed steps, and its processes. Each process uses its app's bearer token, and has an `active_since` timestamp and a type: long-running (sends heartbeats) or short-lived (does not). Serverless functions count as short-lived.
- A probe-only app has no token, steps or processes. It appears under Health and never under LLM spend.

It also has a `sources` section saying which vendor sources are enabled. A sync command, run locally against the production database, writes the file to the `apps` and `settings` tables, and exits with an error on a malformed file without changing anything. An app no longer in the file is removed and its token is revoked. A process no longer in the file is removed while the app's token stays valid, so batches still naming that process are rejected and counted. Historical batches and events stay in both cases. Because the sync is destructive, it prints any planned removals and requires confirmation, and it refuses a file that removes every app unless a flag is given. The note iterates over this registry, so an app that has never sent anything still appears, with its row chosen by the spend table.

**Tokens:** a token is a long random value generated locally, and only its hash goes in `fleet.yaml`. To rotate, add the new hash alongside the old one, sync, deploy the app with the new token, then remove the old hash and sync again.

### Client behaviour (fail-safe)

- Each process that makes LLM calls runs its own client, set up with its `process` name and allowed steps. Each app wraps its LLM client in one place, so call sites are hard to miss.
- Recording an event appends to a bounded in-memory buffer (1,000 events, including any batch waiting to send) and returns immediately. It never throws and never blocks the app, and the whole client body is guarded so an internal bug cannot reach the caller.
- The client checks values when recording. Exceptions map to the `error_class` set through a small function, and anything unrecognised becomes `other`, so a raw exception name never reaches the wire. An event with an unlisted step or invalid value is dropped alone and counted, so it cannot sink the other events in its batch. Server rejection stays as the backstop.
- A background flush runs every 30 seconds, or at 100 events, with a 2-second timeout. A batch holds at most 100 events. Only one batch is in flight or waiting to retry at a time, and when it is accepted the next batch forms straight away if 100 events are waiting.
- When the buffer is full, new events are dropped and counted.
- A batch is frozen when formed, including its `dropped` value, which is the client's discard count at that moment, capped at 1,000,000. That amount is then subtracted from the count, so any remainder goes in the next batch. Retries send the identical payload with the same `batch_id`, so a retry after a lost response cannot lose or double count anything.
- A failed send retries at the next flush. After 3 failures, or on any 4xx (not retried), the batch is discarded, and its event count plus its carried `dropped` value go back into the discard count.
- A long-running process sends an empty batch if nothing else was sent for 5 minutes. It works as a heartbeat.
- A short-lived process calls an awaited `flush()` before it exits. `flush()` always sends at least one batch per run, even if empty, and sends successive batches within one overall 2-second limit. Anything unsent at exit is lost. It sends no heartbeats, so its silence is not treated as a gap. Its healthchecks.io check, if it has one, covers whether it ran.
- A serverless function has no background timer to rely on, so each invocation sends its batch at the end. It hands `flush()` to the platform's `waitUntil` so the user's response is not delayed. If an app cannot do that, its LLM calls wait on the flush for up to 2 seconds, which breaks the rule that telemetry never slows an app, so such a process needs a decision before it gets a client.
- Shutdown flush is best effort. Events buffered during a crash or redeploy are lost without a count, which is accepted because spend is an estimate.

### Collector

- `POST /v1/batches` checks the bearer token and the body size before parsing anything. Unauthenticated requests are limited to 60 per minute per IP. Failed auth is not counted as a rejected batch, because it cannot be tied to an app.
- It writes the batch row and its events in one transaction. A repeated `batch_id` for the same app returns success and writes nothing, so retries are idempotent.
- Rejected batches store no payload. Only a per-app, per-day rejected count is kept, and the note reports it.
- `GET /healthz` checks the database. The Better Stack probe calls this.
- A background loop pings the collector's healthchecks.io check after a successful database check.

Tables:

- `apps(name, monitor_ids, deploy_source, token_hashes, processes, steps)` and `settings(key, value)`, synced from `fleet.yaml`
- `batches(app, process, batch_id, received_at, event_count, dropped)` with a unique key on `(app, batch_id)`
- `events(id, app, process, batch_id, step, model, input_tokens, output_tokens, latency_ms, status, error_class, received_at)`
- `rejected_counts(app, day, count)`
- `subscriptions(name, kind, amount, currency, period, anchor_date)` with a unique key on `name`
- `note_runs(day, claimed_at, sent_at)` with a unique key on `day`

**Retention:** heartbeat-only batches (`event_count` and `dropped` both zero) are deleted after 30 days, since only recent ones are needed to measure gaps. At 288 heartbeats per day per long-running process, that keeps the table small. Events, and batches with events or a dropped count, are kept for v2 history, which is acceptable at 2-4 apps.

### Spend for each app, "$0" versus "no data"

Spend is `input_tokens` and `output_tokens` times a price table kept in the repo, and is always labelled as an estimate. Yesterday means midnight to midnight in the configured timezone.

The table has only as many rows as there are different things to do in the morning. Each app with a client prints the first row that matches:

| Order | Note shows | When | What I do |
|---|---|---|---|
| 1 | `no data`, or `no data (rejected)` | Nothing accepted yesterday, and a report was expected | Check the client or collector |
| 2 | `no runs` | Nothing accepted, nothing rejected, only short-lived processes, and any healthchecks.io check they have was read and shows no run | Nothing |
| 3 | `at least $X.XX est. (<reasons>)` | Some data, with one or more of: `gap`, `dropped`, `rejected`, `unpriced` | Look at the named reason |
| 4 | `$X.XX est.`, including `$0.00 est.` | Everything accepted, nothing missing | Nothing |

- `no data` never prints as a dollar figure, and neither does `no runs`.
- A report is expected from any long-running process, from a short-lived process whose healthchecks.io check recorded a run, and whenever batches were rejected.
- Exact gap times and counts stay in the database. The reason word is enough to know where to look.
- A process whose `active_since` is after yesterday is ignored, and an app with no active process is left out of the section.

**What counts as a `gap`:** more than 1 hour without an accepted batch from a long-running process, measured within yesterday and from its `active_since` if that falls inside the day. A long-running process with no batches at all has a gap, so a never-reporting worker cannot hide behind a healthy web process. Short-lived processes have no gaps.

**What `$0.00 est.` proves:** every long-running process was reaching the collector all day, or a short-lived run reported, and no call was recorded or reported lost. Without the heartbeat, an idle app and a broken client look the same.

**Known blind spots, all accepted because spend is an estimate:**
- A call site outside the app's one LLM wrapper is not counted.
- A crash or redeploy can lose buffered events without a count.
- A short-lived run can lose its batch at exit while other runs report, which understates the figure.
- A serverless app with no healthchecks.io check shows `no runs` for both an idle day and a broken client. It never shows a dollar figure in that case, and the note does not count it as a problem.

### Daily note

Sent every morning, including on good days. If it cannot be delivered, healthchecks.io alerts me instead.

```
PulseOps, Mon 9 Nov: 1 problem

Health (24h)
  app-a  up, 0 incidents, deploy success
  app-b  up, 1 incident (4 min), deploy success
  app-c  up, 0 incidents, deploy success
  site   up, 0 incidents
  workers  3 of 3 reporting

LLM spend yesterday (estimate)
  app-a  $1.82 est.
  app-b  $0.00 est.
  app-c  no data

Due in the next 7 days
  Railway  $20  Thu 12 Nov
  example.com  $14  Sat 14 Nov
```

(The figures above are made up to show the format.)

**Sources:**
- Each vendor source is read separately: Better Stack, healthchecks.io, and each deploy source. An enabled source that fails prints `unknown: <source> unavailable`, and the rest of the note still sends. Postgres is different, because the registry lives there. See step 4 under Run once per day.
- A source can be structurally unavailable, for example if an API does not work on a free tier. In that case it is disabled in `fleet.yaml`, and the sync writes that to `settings`. This removes it from the note body and the headline rule, and a footer line says `Not checked: <source>`. Temporary failures still show as `unknown`.
- Better Stack and healthchecks.io are what make a health claim possible. Deploy status is optional.

**Headline:**
- A **problem** is any of these: an enabled source that did not answer, something down, a latest deploy in `failure`, or a spend line showing `no data` or `at least`. `no runs` is not a problem. Each affected app or source line counts as one problem, however many conditions it has.
- If there is at least one problem, the headline gives the count, such as `1 problem`.
- With no problems, and either health source disabled, the headline is `no problems found`, with the `Not checked` footer.
- With no problems, and Better Stack and healthchecks.io both enabled, the headline is `all clear`. This is the only case that says it.

### Run once per day

All `day` values use the configured timezone, so daylight saving changes do not move rows between days. If the scheduler runs in UTC, the morning send shifts by one hour across a change, which I accept.

1. The job inserts into `note_runs` before sending. The unique key on `day` makes any later run that day exit without sending.
2. It retries delivery within the run, up to 3 times with backoff, on a failure or an ambiguous timeout. A rare duplicate from an ambiguous send is acceptable, because a missing note is worse.
3. On delivery it writes `sent_at` and pings healthchecks.io. If all attempts fail, or the job crashes after the claim, no ping is sent and healthchecks.io alerts me through its own channel. A Postgres failure after the claim, while reading the registry, events or subscriptions, follows this same path.
4. If Postgres is down at claim time, the job retries for a few minutes. It then sends a fixed message without a claim, `PulseOps: database unavailable. Health, spend and subscriptions not checked today. Bought alerts are unaffected.`, using the same delivery retries as step 2. It pings healthchecks.io only after that message is delivered. Without Postgres the job does not know the registry, so this message has no per-app content.

A duplicate can happen in two cases: an ambiguous send in step 2, and the claim-less message here. Both are accepted, because a note arriving twice costs little and a note reporting an outage is worth having.

### Subscriptions

- A git-ignored `subscriptions.yaml` holds the rows. A sync command, run locally against the production database like the fleet sync, upserts them into `subscriptions`, removes rows no longer in the file, and exits with an error on a malformed file without changing the table. The repo commits only `subscriptions.example.yaml`.
- Each row has an anchor date and a period (monthly or yearly), and the next due date is computed. Dates that do not exist in a given month clamp to its last day, whether monthly on the 29th to 31st or yearly on 29 February. This keeps upkeep near zero unless a price or plan changes.
- Domains are rows too, with `kind: domain`. RDAP expiry lookup is not in v1.

### What v2 adds, and why v1 does not block it

| v2 feature | How it builds on v1 |
|---|---|
| LLM latency and errors by step | Already collected. v2 only adds queries and display |
| Detail page | Reads the existing tables. The note can link to it |
| Per-app telemetry beyond LLM calls | New optional `kind` field in schema `v: 2`, with a small migration adding the column, existing rows treated as `llm`, and `model` and token fields becoming optional for other kinds |
| Queue backlog for apps with BullMQ | One new `kind`, sampled on a timer by the same client: job counts per queue, with queue names as a closed set in the registry. This catches a worker that is alive but falling behind, which the v1 ping cannot see |
| Subscription price history | New table of `(name, amount, currency, effective_from)`, appended by the sync when an amount changes. v1 overwrites amounts, so history starts on the day this ships |
| Monthly cost analysis | Reads the kept events and subscriptions. Needs dated prices in the LLM price table, because v1 applies current prices only, and needs the price history above for subscriptions |
| Cost forecast | Built on the monthly analysis, so it needs some months of history first |

Because unknown fields reject the batch, new fields roll out in order: the collector learns `v: 2` first, then clients upgrade. The collector keeps accepting `v: 1`.

Before building by-step LLM tracing, compare it with LLM tracing tools such as Langfuse. This was not researched in this session. Building it for the portfolio is a fine outcome, but it should be a choice.

## Success Criteria

- For 14 consecutive days the note arrives each morning, and I open the old dashboards only to act on something the note or an alert told me.
- Stopping a worker in a test produces an alert from healthchecks.io within its configured grace period, not the next morning.
- Disabling the note job produces a healthchecks.io alert.
- Tests prove:
  - An unknown field or invalid value, in the envelope or an event, rejects the whole batch and stores no payload.
  - A repeated `batch_id` writes nothing new, and a timeout followed by a retry neither loses nor double counts `dropped`.
  - With the collector down or hanging, the client never throws and returns immediately, and its buffer stays within the bound, including while a batch waits to retry.
  - A batch never exceeds 100 events, and an invalid event at record time is dropped alone.
  - Each row in the spend table above is produced by its condition, including `no data` and `no runs` never printing a dollar figure, a never-reporting worker beside a healthy web client, a process started mid-day, a process starting after yesterday beside active ones, an app with only short-lived processes, a short-lived job that ran while the collector was down, a short-lived app with all batches rejected, and all event batches rejected while heartbeats succeed.
  - A probe-only app appears under Health, never under LLM spend, and never counts as `no data`.
  - Each deploy source returns the one `DeployEvent` shape, a failing source gives `unknown`, and a `failure` state counts as a problem.
  - A serverless flush through `waitUntil` does not delay the response.
  - The sync removes an app no longer in `fleet.yaml`, its token stops working, and its history stays.
  - The sync removes a process no longer in `fleet.yaml`, the app's token still works, batches naming that process are rejected and counted, and its history stays.
  - A source disabled in `fleet.yaml` leaves the note body and shows in the footer.
  - `all clear` never appears under any condition the headline rule names: unknown source, disabled health source, down, failed deploy, `no data`, `at least`.
  - A second note run on the same day sends nothing.
  - Delivery failures retry, then withhold the ping. Postgres down at claim time produces the fixed database message, and its ping is sent only after delivery. A Postgres failure after the claim sends no note and no ping.
  - The sync lists removals and needs confirmation, and refuses a file that removes every app unless the flag is given.
  - Oversized integers return a 4xx, and auth and size checks run before parsing.
  - Heartbeat-only batches older than 30 days are deleted, and batches with events or a dropped count stay.
  - `flush()` drains more than 100 buffered events in successive batches within its overall limit, and the carried `dropped` value never exceeds 1,000,000.
- A test sends a batch with a prompt-like value and a UUID in `step` and confirms that both are rejected.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: MAX_ITERATIONS

### R3-1 — consistency (blocking)

**Problem**

> Row 2 prints a $0.00 figure when PulseOps has no evidence of spend either way, and calls it not a problem because healthchecks.io covers missed runs. That check only proves the job ran, not that its telemetry arrived. A short-lived job can run, make paid LLM calls, ping its check, and lose its only batch because the collector was down or flush() hit its 2-second timeout. The process then exits, so no dropped count survives. The app prints $0.00, nothing counts as a problem, and the headline can say 'all clear'. This is the false reassurance the design exists to prevent. It also conflicts with the required test that 'no data' never prints as $0, and with the user's stated choice of 'no data' over '$0'.

**Remedy**

> Remove the figure from this row, for example printing 'no runs reported'. Then decide how a run that was seen by healthchecks.io but has no accepted batch is handled, for example showing 'no data' as a problem when the check recorded a run in the window. If the blind spot is kept deliberately, say so and do not print $0.00. Add a test for a short-lived job that ran while the collector was down.

### R3-2 — completeness (blocking)

**Problem**

> The per-process window handles an active_since inside yesterday, and row 1 handles an app whose processes all start after yesterday. Nothing handles one process starting after yesterday in an app with other active processes. Example: a worker is added at 06:00 today with active_since 06:00, and the note runs at 07:00 covering yesterday. Its active_since does not fall inside the day, so read literally its window starts at midnight, and with no batches it has one full-day gap. That produces a false 'at least' figure and a false problem.
