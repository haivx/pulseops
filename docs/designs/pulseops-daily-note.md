# Design: PulseOps, a daily ops note for a one-person fleet

Generated by /office-hours on 2026-11-09
Branch: main
Repo: haivx/pulseops
Status: APPROVED
Mode: Builder

## Problem Statement

I run 2-4 production apps of my own. They are new, with few users, and have had no real incident yet. To feel safe I check several places by hand: each app's hosting dashboard, the Anthropic console for LLM usage, the domain registrar, and billing emails for subscriptions. It is hard to keep track of.

The problem is reassurance across too many tabs. It is not diagnosis.

PulseOps is a personal tool. I may later use it to support my own business. There is no revenue goal.

## What Makes This Cool

Ops tools assume you want a console, but a console is one more tab. PulseOps v1 has no console. It is one message each morning, watched by an outside service, so the checker cannot die silently.

## Constraints

- One user, 2-4 apps, hosted on Railway, Vercel or elsewhere. Nothing in the design assumes one host, and apps on one host must not depend on that host's API for their row in the note.
- All apps are TypeScript/Node, so there is one client file.
- The Anthropic account is individual. Anthropic's docs say the Admin API, which holds the usage and cost reports, is unavailable to individual accounts. LLM spend must come from usage the apps log themselves.
- Telemetry must never carry prompts, responses, document IDs or user data.
- Telemetry must never break or slow an app.
- The repo is public. App names, the subscription list and tokens stay out of git.
- v1 stays small, and it must not block v2.

## Premises

Agreed in session:

1. The problem is reassurance across too many tabs. Diagnosis, logs and incident timelines are out of v1.
2. v1 has no console. It is a daily message, and the detail page comes later.
3. Buy probes and dead man's switches. Build only the note, the collector and a hand-kept subscription list. Email parsing is out.
4. LLM spend comes from usage the apps log themselves, because the account is individual.
5. An outside service watches the job, so an outage at a hosting provider cannot silence both the apps and the checker.

## Approaches Considered

### Approach A: Pull from each app
Each app keeps its own usage table and exposes a private endpoint. Rejected: it repeats the work in every app, and v2 would start with a migration to central storage.

### Approach B: Small collector with one events table (chosen)
Apps send usage through a non-blocking client to one ingest endpoint backed by Postgres. A scheduled job reads the table and sends the note.

### Approach C: Structured logs read through Railway's API
Rejected: it depends on log retention and query limits that were not verified, and it ties the data path to Railway.

## Recommended Approach

Approach B. The event shape already carries most of v2's fields, so v2 needs only small additive migrations instead of moving to central storage.

### Build versus buy

| Need | Decision |
|---|---|
| App down, immediate alert | Buy: Better Stack probes (free tier reported at 10 monitors; 2-4 apps plus the collector fits) |
| Worker silent, immediate alert | Buy: one healthchecks.io check per worker (free tier reported at 20 checks) |
| Collector silent | Buy: its own healthchecks.io check, plus a Better Stack probe on its health endpoint |
| Daily note job died | Buy: its own healthchecks.io check |
| Daily note, LLM usage collection, subscriptions due | Build: this is PulseOps |

Immediate alerts go directly from the bought tools to me. PulseOps is never in that path, so a PulseOps bug cannot suppress an alert.

Worker pings are a small change in each app, separate from the PulseOps client. A long-running worker sends an HTTP GET to its healthchecks.io URL with a 2-second timeout and errors ignored: after each job that succeeds, and on a 5-minute timer that fires only while no job is in progress and its queue connection is up. A plain timer would keep pinging in Node while a job hangs, so this rule is what makes a hung job, a worker failing every job, or a lost queue connection go silent. With concurrency above 1, one hung job can hide behind others that complete, which is an accepted blind spot. The check has a 15-minute grace period, which must be set above the longest expected job. A scheduled job pings once on success.

### Components

1. **Client:** one small TypeScript file vendored into each app that makes LLM calls, plus a small `heartbeat.ts` for worker pings, tested in this repo. Apps with no LLM calls, such as a static site on Vercel, are probe-only and have no client.
2. **Collector:** one HTTP service with Postgres, on any host that can also run a scheduled job. The apps' hosts play no part in this choice.
3. **Note job:** a scheduled run that reads all sources and sends one message.

### Commands and exit codes

```
pulseops token new <app>                       print a token once, and the hash line for fleet.yaml
pulseops sync fleet|subscriptions [--dry-run] [--yes]
pulseops doctor                                check the database, each source, delivery and registry references
pulseops verify <app> --process <name>         check auth and registration through POST /v1/verify, with no side effects; reads PULSEOPS_TOKEN
pulseops note [--dry-run | --resend]
```

| Exit code | Meaning |
|---|---|
| 0 | Sent, already sent, or nothing to do |
| 1 | Unexpected failure |
| 2 | Usage or validation error, or confirmation needed with no terminal |
| 3 | Claim held but note not sent; prints the `--resend` command |
| 4 | A dependency is unavailable, including `--dry-run` with Postgres down |

Errors print the operation, a stable `E_*` code and the fix on one line to stderr. No command prints a secret: tokens are shown only by `token new`, and one log scrubber covers database URLs, tokens and healthchecks.io ping URLs.

### Deploy status

Deploy status is optional and is read when the note runs, so there is no webhook endpoint in v1. Every source is normalized to one shape:

```ts
type DeployEvent = {
  app: string;
  source: string; // "github", or a platform adapter's name
  state: "success" | "failure" | "in_progress" | "none" | "unknown";
};
```

- Each app names its source in the registry: `github` (with a repo and the environment name exactly as the host reports it, which on Railway is `<project> / production`), a platform adapter, or `none`.
- GitHub's deployment statuses are the first source, because one adapter can cover any host that reports deployments to GitHub.
- A platform adapter is written only for an app that GitHub cannot cover. Each adapter is one function that takes the app's config and returns a `DeployEvent`.
- An adapter that fails returns `unknown`. If a whole source fails, the note prints one `unknown: <source> unavailable` line. If one app's query fails while the source answers, that app's row shows `deploy unknown`, which counts as one problem.
- GitHub statuses map as: `success` to `success`; `failure` and `error` to `failure`; `queued`, `pending` and `in_progress` to `in_progress`, or `unknown` if older than 1 hour. `inactive` is skipped in favour of the next status. Anything else maps to `unknown`. For an app configured as `github`, finding no deployment maps to `unknown`, so a mistyped environment cannot silently remove the line. A latest deployment with no statuses maps to `none` if it is older than 90 days, because GitHub deletes statuses after 90 days, and to `unknown` otherwise. `none` is only for an app configured as `none`.
- The note prints `latest deploy: success`, `latest deploy: failure`, `latest deploy: in progress` or `latest deploy: unknown`, and nothing for `none`. Only the latest deploy that is not `inactive` counts. The wording is "latest deploy", not "deploy failed", because Railway also posts `failure` when a service crashes after a deploy, and posts it to older deployments too.

### Event schema (strict allow-list)

Batch envelope, and no other fields:

| Field | Rule |
|---|---|
| `v` | exactly `1` |
| `batch_id` | a UUID |
| `app` | a registered app name that matches the app bound to the bearer token |
| `process` | a process name registered for that app, such as `web` or `worker` |
| `dropped` | integer from 0 to 1,000,000 |
| `events` | array of 0 to 100 events |

Event fields, and no others:

| Field | Rule |
|---|---|
| `step` | one of the steps registered for that app, or the reserved value `other` |
| `model` | matches `^[a-z0-9_.:-]{1,64}$` |
| `input_tokens`, `output_tokens` | integers from 0 to 10,000,000 |
| `cache_read_tokens`, `cache_creation_tokens` | optional integers from 0 to 10,000,000 |
| `latency_ms` | integer from 0 to 3,600,000 |
| `status` | `ok` or `error` |
| `error_class` | one of `rate_limited`, `timeout`, `overloaded`, `auth`, `invalid_request`, `server_error`, `other`. Required when `status` is `error`, absent otherwise |

- Any unknown field or invalid value, at either level, rejects the whole batch. A batch over 256 KB is also rejected.
- **What the boundary guarantees:** field names, `step` and `error_class` are closed sets enforced by the server, so a document ID or user value cannot pass through them. `model` is only a shape check, so a value such as `doc-8841` would match. The rule that keeps it clean is that `model` comes from code or config, never from user input. `model` is not a closed set because a new model should show as `unpriced` in the note instead of losing the batch.
- Adding a step means syncing the registry first, then deploying the app. A client whose list is behind records the event with step `other`, so spend stays correct. A client ahead of the registry has its batch rejected with `unknown_step`, which the note names.
- Error messages are never sent.
- The server records the time a batch was received and uses it to assign events to a day. Events carry no timestamp of their own, which keeps to the agreed field list. Events flushed just after midnight count toward the new day, which is acceptable for an estimate.
- `dropped` is a count of events the client discarded, as defined under client behaviour. It carries no event content.
- **Why v1 collects fields the note does not use:** `step`, `latency_ms` and `error_class` serve v2, while `status` also drives the LLM failure problem in the note. I am keeping them so v2 starts with real history. The cost is keeping the step list current, and a missed step only falls back to `other`. Deferring them through the `v: 2` rollout would shrink v1, but that history would be lost.

### App registry

A git-ignored `fleet.yaml` is the only list of what exists, and the repo commits only `fleet.example.yaml`. For each app it holds:

- The name, matching `^[a-z0-9-]{1,32}$` so token prefixes parse unambiguously, its required Better Stack monitor ID, and a `checks` list of its healthchecks.io checks: one per worker, job or service, whether or not that process has a client. The workers line iterates over this list, so a dead worker with no LLM calls still shows.
- Its deploy source, as described under Deploy status.
- For an app with a client: one token hash, its allowed steps, and its processes. Only processes with a client are listed here. Each uses its app's bearer token, and has an `active_since` timestamp, a type and the name of its entry in `checks`, if it has one. The type is long-running (sends heartbeats), short-lived (sends a batch every run) or serverless (sends a batch only when it made an LLM call). Set `active_since` to the expected first deploy; if it is set early, the first day can show a false `gap`, which is accepted.
- A probe-only app has no token, steps or processes, and can still have `checks`. It appears under Health and never under LLM spend.
- PulseOps' own collector is listed as a probe-only app with one entry in `checks`, so a collector that is down that morning shows as a problem.

It also holds the enabled vendor sources, the timezone, and per-app thresholds for LLM failures and daily spend. The host's scheduler sets the send time. A sync command, run locally against the production database through a dedicated role limited to the `apps`, `settings` and `subscriptions` tables and over verified TLS, writes the file to the `apps` and `settings` tables, and exits with an error on a malformed file without changing anything. An app no longer in the file is removed and its token is revoked. A process no longer in the file is removed while the app's token stays valid, so batches still naming that process are rejected and counted. Historical batches and events stay in both cases. Because the sync is destructive, it prints the target database host and any planned removals and requires confirmation or `--yes`. With no terminal and no `--yes` it exits 2 and lists the removals. It refuses a file with no apps. It validates the whole file first and reports every problem with its line and fix, and it writes in one transaction, so it is safe to re-run. It warns when `active_since` is more than 30 days ahead. The note iterates over this registry, so an app that has never sent anything still appears, with its row chosen by the spend table.

**Tokens:** `pulseops token new <app>` generates a token shaped `po_<app>_<random>`, with at least 128 bits of randomness, and prints it once, with the SHA-256 hash line for `fleet.yaml`. Hashes are compared in constant time. The `<app>` prefix is not secret, and it lets a failed auth be counted against that app. To rotate, replace the hash, sync, and deploy the app with the new token. Batches rejected during that short cutover are lost, which is accepted.

### Client behaviour (fail-safe)

```ts
const pulse = createPulseClient({ url, token, app, process, type, steps });   // type: "long-running" | "short-lived" | "serverless"
const reply = await pulse.track("summarize", () => anthropic.messages.create(params));
await pulse.flush();   // resolves to { sent, discarded, lastErrorCode }, and never rejects
pulse.stats();         // counts, last error code, first internal stack; local only
```

Node 18 or later, with no runtime dependencies. Edge runtimes are unsupported unless tested. The README shows one complete wrapper for normal and streaming calls.

- **Off switch:** with no `url` or `token`, or with `PULSEOPS_DISABLED=1`, the client makes no network calls and warns once. This keeps local runs, test suites and preview deploys out of production data.
- **Process type:** `type` is required and decides the client's behaviour: heartbeats for long-running, one batch per run for short-lived, and no batch without an LLM call for serverless. `pulseops verify` compares it with the registry.
- **Streams:** `track` passes the stream through untouched and records when it ends, with `latency_ms` measured to the last chunk. An abandoned stream never delivers final usage, so it counts as a discarded event. An error after a 200 records `status: error`. SDK-internal retries are one event. `model` is the requested model ID, normalized before price lookup, and `flush` runs after the stream ends. The caller's return value and exceptions are unchanged.
- **Seeing failures:** the client writes one rate-limited stderr line per process with a code and fix and never a value, such as `pulseops E_AUTH: collector rejected token for app=x; fix: run pulseops verify x`. `PULSEOPS_DEBUG=1` writes more.

- Each process that makes LLM calls runs its own client, set up with its `process` name and allowed steps. Each app wraps its LLM client in one place, so call sites are hard to miss.
- Recording an event appends to a bounded in-memory buffer (1,000 events, including any batch waiting to send) and returns immediately. It never throws and never blocks the app, and the whole client body is guarded so an internal bug cannot reach the caller. An internal error counts as a discarded event, so it prints `at least (dropped)` and never a clean figure.
- The client checks values when recording. Exceptions map to the `error_class` set through a small function, and anything unrecognised becomes `other`, so a raw exception name never reaches the wire. An unlisted step becomes `other`. An event with any other invalid value is dropped alone and counted, so it cannot sink the other events in its batch. Server rejection stays as the backstop.
- A background flush runs every 30 seconds, or at 100 events, with a 2-second timeout. A batch holds at most 100 events. Only one batch is in flight or waiting to retry at a time, and when it is accepted the next batch forms straight away if 100 events are waiting.
- When the buffer is full, new events are dropped and counted.
- A batch is frozen when formed, including its `dropped` value, which is the client's discard count at that moment, capped at 1,000,000. The count then resets to zero. Retries send the identical payload with the same `batch_id`, so a retry after a lost response cannot lose or double count anything, with one accepted exception: if a batch commits but every response is lost until it expires, its events also go into the discard count.
- A network failure, 5xx, 408 or 429 keeps the batch and retries at the next flush, honouring `Retry-After` up to the flush interval, for up to 30 minutes, so a normal deploy or short outage loses nothing. After 30 minutes, or on any other 4xx (not retried), the batch is discarded, and its event count plus its carried `dropped` value go back into the discard count.
- A long-running process sends an empty batch if nothing else was sent for 5 minutes. It works as a heartbeat. All client timers are `unref()`-ed, so idle timers cannot keep a process from exiting. An in-flight send can hold it for at most its 2-second timeout.
- A short-lived process calls an awaited `flush()` before it exits. For this type, `flush()` always sends at least one batch per run, even if empty, and sends successive batches within one overall 2-second limit. Anything unsent at exit is lost. It sends no heartbeats, so its silence is not treated as a gap. Its healthchecks.io check, if it has one, covers whether it ran.
- A serverless function has no background timer to rely on, so only an invocation that made an LLM call sends a batch, at its end, and an invocation with no LLM call sends nothing. A serverless process's check is therefore not evidence that a batch was expected. Each runtime instance has its own client, so "one batch in flight" holds per instance. It hands `flush()` to the platform's `waitUntil` so the user's response is not delayed. If an app cannot do that, its LLM calls wait on the flush for up to 2 seconds, which breaks the rule that telemetry never slows an app, so such a process needs a decision before it gets a client.
- Shutdown flush is best effort. Events buffered during a crash or redeploy are lost without a count, which is accepted because spend is an estimate.

### Collector

- `POST /v1/batches` checks the bearer token and the body size before parsing anything. Every failed auth returns an identical 401. One whose token prefix names a registered app counts as reason `auth` for that app, so a wrong token can never read as an idle app. Because the prefix is not secret, `auth` only prints when nothing was accepted that day. If batches were accepted, it is logged and changes nothing in the note.
- Any database error during auth or validation returns 503, never a 4xx, so a database blip cannot make clients discard data.
- A rejected batch gets its status and an RFC 9457 body with a closed `code` and the field path, never the value.
- It writes the batch row and its events in one transaction. A repeated `batch_id` for the same app returns success and writes nothing, so retries are idempotent.
- Rejected batches store no payload. Only a count per app, day and reason code is kept, and the note reports the reason.
- `POST /v1/verify` runs auth and validation only, and writes nothing.
- `GET /healthz` performs a small database write, so a full disk or read-only database fails it, and returns a 503 with a code and no driver text on failure. The Better Stack probe calls this.
- The collector and note job log rejected-batch reasons and source failures to stdout, with the field name or source, a code and the HTTP status, and never a value.
- A background loop pings the collector's healthchecks.io check after the same write succeeds.

Tables:

- `apps(name, monitor_id, checks, deploy_source, token_hash, processes, steps)` and `settings(key, value)`, synced from `fleet.yaml`
- `batches(app, process, batch_id, received_at, event_count, dropped)` with a unique key on `(app, batch_id)` and an index on `(app, process, received_at)`
- `events(id, app, process, batch_id, step, model, input_tokens, output_tokens, latency_ms, status, error_class, received_at)` with an index on `(app, received_at)`
- `rejected_counts(app, day, reason_code, count)`
- `subscriptions(name, kind, amount, currency, period, anchor_date)` with a unique key on `name`
- `note_runs(day, claimed_at, sent_at)` with a unique key on `day`

**Retention:** everything is kept. At 288 heartbeats per day per long-running process, that is under a million rows a year at 2-4 apps, which is accepted.

### Spend for each app, "$0" versus "no data"

Spend is each token count, including cache reads and cache creation, times its rate in a price table kept in the repo, and is always labelled as an estimate. Yesterday means midnight to midnight in the configured timezone.

The table has only as many rows as there are different things to do in the morning. Each app with a client prints the first row that matches:

| Order | Note shows | When | What I do |
|---|---|---|---|
| 1 | `no data`, or `no data (rejected: <reason>)` | Nothing accepted yesterday, and a report was expected, with any long-running process active for more than 1 hour of the day | Check the client or collector, or fix the named reason |
| 2 | `not checked` | Nothing accepted, nothing rejected, no long-running process, and a short-lived process has a healthchecks.io check that could not be read | Fix or wait for the source |
| 3 | `no runs` | Nothing accepted, nothing rejected, no long-running process, and every short-lived process's check was read and shows no run, or there are only serverless processes | Nothing |
| 4 | `at least $X.XX est. (<reasons>)` | Some data, with one or more of: `gap`, `missing`, `dropped`, `rejected`, `unpriced`, `not checked` | Look at the named reason |
| 5 | `$X.XX est.`, including `$0.00 est.` | Batches were accepted and nothing is missing | Nothing |

- `no data`, `not checked` and `no runs` never print a dollar figure, and `$0.00 est.` requires an accepted batch.
- `missing` means a short-lived process whose check recorded a run yesterday has no accepted batch, even if other processes reported. Serverless processes never count as `missing`.
- `not checked` as a reason means a short-lived process's check could not be read, so a lost batch cannot be ruled out. It is never counted as its own problem, because the source line or the `Not checked` footer already covers it.
- A report is expected from any long-running process, from a short-lived process (not serverless) whose healthchecks.io check recorded a run, and whenever batches were rejected.
- Exact gap times and counts stay in the database. The reason word is enough to know where to look.
- A process whose `active_since` is after yesterday is ignored, and an app with no active process is left out of the section.

**What counts as a `gap`:** more than 1 hour without an accepted batch from a long-running process, measured within yesterday and from its `active_since` if that falls inside the day. A long-running process with no batches for more than 1 hour of that window has a gap, so a never-reporting worker cannot hide behind a healthy web process. Short-lived processes have no gaps.

**What `$0.00 est.` proves:** every long-running process was reaching the collector all day, each short-lived process with a recorded run reported, and no call was recorded or reported lost. Without the heartbeat, an idle app and a broken client look the same.

**Note logic:** this is one pure function, `gather() -> classify(inputs) -> render()`, with no I/O inside `classify`, so the spend and headline rules are tested as a table with an injected clock. Day bounds are computed once in the configured timezone.

**Known blind spots, all accepted because spend is an estimate:**
- Several replicas share one `process` name, so one dead replica can hide behind the others.
- A drop near midnight is reported by a later batch, so it can mark the wrong day.
- A call site outside the app's one LLM wrapper is not counted.
- A crash or redeploy can lose buffered events without a count.
- A short-lived process can lose one run's batch at exit while its other runs report, which understates the figure.
- A short-lived process with no healthchecks.io check, including any serverless function, cannot be told apart from a broken client. An app with only such processes shows `no runs` and no dollar figure, and that is not a problem. Beside a healthy process, its lost batches understate the figure.

### Daily note

Sent every morning, including on good days. If it cannot be delivered, healthchecks.io alerts me instead.

```
PulseOps, Mon 9 Nov: 1 problem
  app-c: no data. Check the client or collector

Health (24h)
  app-a  up, 0 incidents, latest deploy: success
  app-b  up, 1 incident (4 min), latest deploy: success
  app-c  up, 0 incidents, latest deploy: success
  site   up, 0 incidents
  collector  up, 0 incidents
  workers  3 of 3 reporting now (failed workers are named here)

LLM spend yesterday (estimate)
  app-a  $1.82 est.
  app-b  $0.00 est.
  app-c  no data

Due in the next 7 days
  Railway  $20  Thu 12 Nov
  example.com  $14  Sat 14 Nov
```

(The figures above are made up to show the format.)

Every problem is listed under the headline with its next action. If nothing is due, that section says `Nothing due in the next 7 days`. An empty subscriptions table prints `No subscriptions configured` and counts as a problem, so a wrong file cannot read as nothing due. If no app has a client, the LLM spend section is left out.

**Sources:**
- Each vendor source is read separately with a 10-second timeout: Better Stack, healthchecks.io, and each deploy source. Better Stack filters incidents by date only (`from` and `to` are `YYYY-MM-DD`), so the job fetches yesterday and today and keeps incidents whose start falls in the last 24 hours. API keys are environment variables on the note job. An enabled source that fails prints `unknown: <source> unavailable`, and the rest of the note still sends. Postgres is different, because the registry lives there. See step 4 under Run once per day.
- A source can be structurally unavailable, for example if an API does not work on a free tier. In that case it is disabled in `fleet.yaml`, and the sync writes that to `settings`. This removes it from the note body and the headline rule, and a footer line says `Not checked: <source>`. Temporary failures still show as `unknown`. Vendor statuses use an allow-list: a healthchecks.io check counts as reporting only when it is `up` or `grace`, and a Better Stack monitor counts as up only on its explicit up status. Any other status, including a new, never-pinged, paused or missing check, shows `unknown` on its own line and counts as one problem, so a check that was never wired can never read as healthy.
- Better Stack and healthchecks.io are what make a health claim possible. Deploy status is optional.

**Headline:**
- A **problem** is any of these: an enabled source that did not answer (one line and one problem, however many apps it affects), a monitor or check shown as `unknown`, a monitor currently down, a check past its grace period (a named failed worker), a latest deploy in `failure` or `unknown`, an app over its LLM failure threshold, an app over its daily spend ceiling, or a spend line showing `no data` or `at least`, except `at least` for `not checked` alone, or for `dropped` alone within tolerance (at most 5 events or 1% of the day's calls, whichever is larger). A resolved incident, a recovered worker, and `no runs` are not problems. Each affected app, worker or source line counts as one problem, however many conditions it has.
- **LLM health is part of the note:** telemetry arriving is not the same as the product working. An app is over its failure threshold when at least 10 calls were recorded yesterday and more than half had `status: error`, printed as `app-a  $0.00 est. (31 of 40 calls failed)`. An app is over its ceiling when its estimate passes the daily limit set for it, printed as `app-a  $400.00 est. (over $20 ceiling)`. Both numbers can be changed per app in `fleet.yaml`.
- If there is at least one problem, the headline gives the count, such as `1 problem`.
- With no problems, and either health source disabled, the headline is `no problems found`, with the `Not checked` footer.
- With no problems, and Better Stack and healthchecks.io both enabled, the headline is `all clear`. This is the only case that says it.

### Run once per day

All `day` values use the configured timezone, so daylight saving changes do not move rows between days. If the scheduler runs in UTC, the morning send shifts by one hour across a change, which I accept.

1. The job inserts into `note_runs` before sending. The unique key on `day` makes any later scheduled run that day exit without sending. After an alert, a manual `--resend` run writes the claim if none exists, sends the note if that day's `sent_at` is empty, then writes `sent_at` and pings healthchecks.io, which clears the alert.
2. It retries delivery within the run, up to 3 times with backoff, on a failure or an ambiguous timeout. A rare duplicate from an ambiguous send is acceptable, because a missing note is worse.
3. Reads after the claim retry for up to 2 minutes. On delivery it pings healthchecks.io, even if writing `sent_at` then fails, and writes `sent_at`. If all attempts fail, or the job crashes after the claim, no ping is sent and healthchecks.io alerts me through its own channel. A Postgres failure after the claim, while reading the registry, events or subscriptions, follows this same path, and so does an empty `apps` table or missing `settings`, so an empty registry can never produce `all clear`.
4. If Postgres is down at claim time, the job retries for 5 minutes. The note job's healthchecks.io grace period must exceed this plus the source timeouts. It then sends a fixed message without a claim, `PulseOps: database unavailable. Health, spend and subscriptions not checked today. Bought alerts are unaffected.`, using the same delivery retries as step 2. It pings healthchecks.io only after that message is delivered, and exits 0. The job must run with automatic restart off, since this message has no claim to stop a repeat. Without Postgres the job does not know the registry, so this message has no per-app content.

A duplicate can happen in two cases: an ambiguous send in step 2, and the claim-less message here. Both are accepted, because a note arriving twice costs little and a note reporting an outage is worth having.

**Recovery after midnight:** `--resend --day YYYY-MM-DD` targets an earlier day.

**Dry run:** `--dry-run` reads every source, ignores any existing claim, prints the note, writes no claim, sends nothing and pings nothing. With Postgres down it prints the fixed message. This is how to check a note before it goes out.

### Subscriptions

- A git-ignored `subscriptions.yaml` holds the rows. `pulseops sync subscriptions`, run locally against the production database like the fleet sync, upserts them into `subscriptions` and removes rows no longer in the file. It follows the same preview, `--yes`, validation and transaction rules, and it refuses an empty file. The repo commits only `subscriptions.example.yaml`.
- Each row has an anchor date and a period (monthly or yearly), and the next due date is computed. Dates that do not exist in a given month clamp to its last day, always computed from the anchor date so 31 January never drifts to the 28th, whether monthly on the 29th to 31st or yearly on 29 February. This keeps upkeep near zero unless a price or plan changes. A due date rolls forward once it passes, so a failed renewal disappears from the note; this is an accepted blind spot, and the renewal itself emails you.
- Domains are rows too, with `kind: domain`. RDAP expiry lookup is not in v1.

### What v2 adds, and why v1 does not block it

| v2 feature | How it builds on v1 |
|---|---|
| LLM latency and errors by step | Already collected. v2 only adds queries and display |
| Detail page | Reads the existing tables. The note can link to it |
| Per-app telemetry beyond LLM calls | New optional `kind` field in schema `v: 2`, with a small migration adding the column, existing rows treated as `llm`, and `model` and token fields becoming optional for other kinds |
| Queue backlog for apps with BullMQ | One new `kind`, sampled on a timer by the same client: job counts per queue, with queue names as a closed set in the registry. This catches a worker that is alive but falling behind, which the v1 ping cannot see |
| Subscription price history | New table of `(name, amount, currency, effective_from)`, appended by the sync when an amount changes. v1 overwrites amounts, so history starts on the day this ships |
| Monthly cost analysis | Reads the kept events and subscriptions. Needs dated prices in the LLM price table, because v1 applies current prices only, and needs the price history above for subscriptions |
| Cost forecast | Built on the monthly analysis, so it needs some months of history first |

Because unknown fields reject the batch, new fields roll out in order: the collector learns `v: 2` first, then clients upgrade. The collector keeps accepting `v: 1`.

Before building by-step LLM tracing, compare it with LLM tracing tools such as Langfuse. This was not researched in this session. Building it anyway is a fine outcome, but it should be a choice.

- For 14 consecutive days the note arrives each morning, and I open the old dashboards only to act on something the note or an alert told me, compared with the baseline recorded in the Assignment.

- Stopping a worker in a test produces an alert from healthchecks.io within its period plus grace (20 minutes on the default settings), not the next morning.
- Disabling the note job produces a healthchecks.io alert.
- Tests prove:
  - An unknown field or invalid value, in the envelope or an event, rejects the whole batch and stores no payload.
  - A repeated `batch_id` writes nothing new, and a timeout followed by a retry neither loses nor double counts `dropped`.
  - With the collector down or hanging, the client never throws and returns immediately, and its buffer stays within the bound, including while a batch waits to retry.
  - A batch never exceeds 100 events, and an invalid event at record time is dropped alone.
  - Each row in the spend table above is produced by its condition, including `no data` and `no runs` never printing a dollar figure, a never-reporting worker beside a healthy web client, a process started mid-day, a process starting after yesterday beside active ones, an app with only short-lived processes, a short-lived job that ran while the collector was down beside a healthy long-running process (`missing`), an unreadable healthchecks.io check (`not checked`), a short-lived app with all batches rejected, and all event batches rejected while heartbeats succeed.
  - A probe-only app appears under Health, never under LLM spend, and never counts as `no data`.
  - Each deploy source returns the one `DeployEvent` shape, a failing source gives `unknown`, and a `failure` state counts as a problem.
  - A serverless flush through `waitUntil` does not delay the response.
  - The sync removes an app no longer in `fleet.yaml`, its token stops working, and its history stays.
  - The sync removes a process no longer in `fleet.yaml`, the app's token still works, batches naming that process are rejected and counted, and its history stays.
  - A source disabled in `fleet.yaml` leaves the note body and shows in the footer.
  - `all clear` never appears under any condition the headline rule names, tested one at a time, including `deploy unknown`, a `new` check and an empty registry.
  - One healthchecks.io outage with 3 short-lived apps counts as exactly 1 problem.
  - A deleted or paused monitor or check shows `unknown`, and a dead worker with no client is named.
  - GitHub `error` maps to `failure`, and an unrecognised status maps to `unknown`. A latest deployment with no statuses maps to `none` when older than 90 days and `unknown` otherwise.
  - Better Stack incidents from a two-day fetch are filtered to the last 24 hours, including one that started just before midnight.
  - Client timers do not keep a short-lived process from exiting.
  - A serverless process with a recorded run and no LLM call prints `no runs`, not `no data`.
  - A second scheduled note run on the same day sends nothing, and `--resend` sends only when `sent_at` is empty.
  - A dry run leaves `note_runs` unchanged and makes no delivery or healthchecks.io call.
  - Each process type behaves as stated, and a serverless `flush()` with no LLM call sends nothing.
  - Normal, streaming, abandoned and mid-stream-error calls record correctly, and the caller's return value and exception are unchanged.
  - With Postgres down, auth returns 503 and the client keeps the batch. A 3-minute collector restart loses nothing and makes no problem.
  - A forged `po_<app>_x` request changes nothing in the note for an app with accepted batches, and `verify` writes nothing.
  - Read-only or full-disk Postgres fails `/healthz`.
  - Two note runs racing on the claim send one note, and the same `batch_id` sent concurrently writes once.
  - 23-hour and 25-hour days, and a batch received exactly at midnight, count correctly in a non-UTC timezone.
  - One end-to-end test goes from a real client through a real collector and Postgres to the note, restarting the collector mid-run.
  - Recorded vendor fixtures, including an unknown status and a changed response shape, give `unknown`.
  - A worker failing every job, or with a lost queue connection, stops pinging.
  - A serverless app with a bad token and nothing accepted prints `no data (rejected: auth)`, never `no runs` or `all clear`.
  - A throw inside `record()` makes the next batch carry `dropped` above 0.
  - With no terminal and no `--yes`, the sync exits 2 and changes nothing. A failure mid-sync leaves the database unchanged.
  - A disabled client makes no network calls, and `flush()` reports its result without rejecting.
  - Network failures, 5xx, 408 and 429 keep the batch for up to 30 minutes, and other 4xx responses do not retry.
  - A known database URL, token and ping URL never appear in any command output or log.
  - Each command returns its documented exit code.
  - An empty subscriptions table is a problem, and the sync refuses an empty file.
  - A hanging vendor source times out and prints `unknown`, and the rest of the note sends.
  - A worker with a hung job stops pinging.
  - Next due dates, month-end and 29 February clamps, the 7-day window edges, subscription removal and a malformed subscriptions file are covered.
  - All calls failing makes a problem even at `$0.00 est.`, and fewer than 10 calls never does. An estimate over the ceiling makes a problem. An unlisted step records as `other` and the batch is accepted.
  - Delivery failures retry, then withhold the ping. Postgres down at claim time produces the fixed database message, and its ping is sent only after delivery. A Postgres failure after the claim sends no note and no ping.
  - The sync lists removals and needs confirmation, and refuses a file with no apps.
  - Oversized integers return a 4xx, and auth and size checks run before parsing.
  - `flush()` drains more than 100 buffered events in successive batches within its overall limit, and the carried `dropped` value never exceeds 1,000,000.
